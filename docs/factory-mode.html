Same planning front half. After tickets are approved, the workflow offers to install a factory: an Orca automation that keeps building ready tickets in parallel until you pause it.

Your four controls

Install

Creates one Orca automation and factory.json. Offered after /to-tickets is approved.

factory install

Pause

Drain: nothing new starts; in-flight tickets finish, then pause.
Stop: interrupts mid-ticket; work stays and resumes from the ledger.

factory pause [--now]

Resume

Runs until the queue is empty, then final review, then pauses itself.

factory resume

One cycle, then pause

Runs one wave now (every ticket ready right now), then sets itself back to paused.

factory cycle

Disabling the automation in Orca's UI is also a hard pause. Every session start in that repo prints one line: factory: paused · 4 ready · 1 needs you.

Code owns the loop

From Super Simple Software Factory: no LLM decides what runs next, whether a ticket passed, or when to pause. Those rules run as written and cost no tokens.

Branch claims

tick claims a ticket by creating factory/<ticket-id> from the integration tip. It fails if the branch exists, so no ticket starts twice. With a remote, the first push wins.

Gate script

Per project: .engineering-workflow/gates.sh, last line GATES: PASS or GATES: FAIL <checks>. A missing required check is a FAIL. tick re-runs it before merging and trusts only its own run.

Review-pile cap

stop_if_waiting = 5. When gates, high-radius approvals and capped tickets reach 5, tick starts nothing new: held: 5 waiting on you. It carries on once you clear the pile.

Build queue

Workers and tick run gates.sh only via factory gate, which holds one of build_slots (default 1) lock-file slots. Queue wait is logged per ticket and doesn't count toward max_minutes.

What slowed it down

Each worker reports one --slowed-by line. The cycle digest lists them next to total queue wait, so the bottleneck is visible, not guessed.

Worker brief

ew-factory is now one-ticket SDD: ponytail + TDD, gates.sh, a fresh Sonnet reviewer that proves the new test fails without the change, one fix round, then factory report.

Per-ticket limits

Turn cap

100 turns per ticket (implementer + fix round), counted by the workflow's PostToolUse hook when EW_FACTORY_TICKET is set. 90 minutes wall-clock backstop via worker-stop.

A capped ticket goes to Needs you with its last failing output, plus one question: what factory change would have prevented this? The answer goes to the Idea Shelf.

Blast radius

/to-tickets tags each ticket low / medium / high; you approve it with the tickets.

high tickets stop at Needs you after review passes: you approve the merge into the integration branch. Shown on the Orca card and in the digest. v3 auto-merge reads the same field.

RadiusTouches
lowone component or module inside one service, no shared code
mediumshared code inside one service, or a public interface other code calls
highdatabase schema or data, auth, payments, secrets, the design system, or more than one service

Guard rails

Never

Merges or pushes to main, deploys, publishes issues, or uses bypass permissions. Install refuses if unattended runs would need bypass mode.

Spend

Same token budget as today. Adds daily_ticket_cap (default 10) and concurrency 3. Hitting the cap drains and pauses.

Memory

No long-lived agent: tick is code and each ticket worker is fresh. State lives in the ledger and factory.json, so nothing depends on chat history.
